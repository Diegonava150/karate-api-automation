# The ledger of which negative tests have been watched failing.
#
# Every scenario listed under `expect:` MUST fail when the suite runs against init-weakened.sql.
# The "Prove the negative tests can fail" job reads this file and requires each one by name.
# Requiring only that the suite went red would be satisfied by a single surviving failure while
# every other mutation quietly stopped being caught — "something failed" is not the claim worth
# making. "Each of these sixteen assertions has teeth" is.
#
# Names are Karate's own, copied from a real mutation run rather than guessed. A Scenario Outline
# collapses to its base name, which is why the four out-of-range ratings and the three malformed
# emails each appear once.
#
# This file cannot go stale unnoticed. The same job cross-checks it against every scenario tagged
# @negative in the suite: add one without accounting for it here and the build fails. That is the
# whole reason the tag exists — before this, four of the five tag families in the repository
# selected nothing at all and were config that looked like a feature.

expect: Creating a book without a required field is rejected
expect: Creating a book with a duplicate ISBN is rejected
expect: Creating a book with a negative price is rejected
expect: Creating a book with no pages is rejected
expect: Updating a book into a duplicate ISBN is rejected
expect: A rating outside one to five is rejected
expect: A review with no reviewer is rejected
expect: A review whose reviewer is only whitespace is rejected
expect: A rating cannot be corrected out of range
expect: An author with a duplicate email is rejected
expect: An email that is not an email is rejected
expect: An author with no name is rejected
expect: An author whose name is only whitespace is rejected
expect: An author with no country is rejected
expect: An author cannot be updated into a duplicate email

# Not a negative scenario, and the most interesting entry here.
#
# The consumer contract requires a duplicate ISBN to come back as 409 with SQLSTATE 23505. With
# the unique index removed the provider answers 201, so the contract fails against the *real
# service* — the same machinery that catches mock drift, working in the other direction. The mock
# keeps passing, because the mock still honours the contract, and the difference between the two
# runs points straight at the provider.
expect: the real service satisfies the consumer contract

# ---------------------------------------------------------------------------------------------
# Negative scenarios this technique cannot reach. Listed rather than omitted, so the cross-check
# above can tell "accounted for" apart from "forgotten".

not-coverable: Creating a book against an author who does not exist is rejected
not-coverable: A review against a book that does not exist is rejected

# Both assert 23503, and both are backed by foreign keys that init-weakened.sql deliberately
# leaves alone. Dropping those keys would prove the assertions can fail and would simultaneously
# delete the capability the rest of the suite is built on: PostgREST derives its embeddable
# relationships from exactly these constraints, so every scenario in embedding.feature would fail
# for an unrelated reason.
#
# A mutation whose blast radius is the whole suite says nothing about the one assertion it was
# aimed at. Worth having, then — just not provable this way.

# ---------------------------------------------------------------------------------------------
# Authorisation, which this technique cannot reach for a different reason.
#
# These assert that a request is *refused* — 401 unauthenticated, 403 authenticated but not
# permitted — and every one of them is enforced by a GRANT rather than by a constraint. The
# weakened schema removes constraints and leaves the permission model untouched, deliberately:
# stripping GRANTs would refuse every write in the suite and turn a targeted mutation into a
# blackout.
#
# They are still watched failing, just by a different mechanism. Removing the writer token from
# one create scenario produced 401 where 201 was expected, which is how the thirty-nine auth
# headers added across the suite are known to matter rather than merely to be present.

not-coverable: An anonymous write is refused
not-coverable: An anonymous delete is refused
not-coverable: A reader token cannot write
not-coverable: A reader token cannot delete
not-coverable: An expired token is refused
not-coverable: A token signed with the wrong key is refused
not-coverable: A malformed token is refused
not-coverable: A reader token cannot be used to escalate by asking for a different role
